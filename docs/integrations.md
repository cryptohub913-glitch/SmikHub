# Подключение интеграций

В SmikHub несколько интеграций, которые нужно настроить руками, чтобы платформа заработала
не только «на бумаге»: **Send Crypto Pay** (реальные деньги в «Кабинете»), **check-бот**
(реальная проверка вступлений в «Купить ОП») и сети-источники спонсоров
**Flyer / Tgrass / PiarFlow** (реальная выдача задач в ботах «Продать ОП» через
`/api/v1/bot/sponsors`). Все — опциональны в том смысле, что бот и API стартуют без них, но
соответствующие разделы будут honestly отключены с понятным сообщением, а не притворяться
рабочими.

---

## 0. Персистентность БД (почему после деплоя могут слетать все подключённые боты)

SmikHub по умолчанию хранит всё в файле SQLite (`DATABASE_URL` в `.env`). Это касается не
самой интеграции, а того, чтобы данные вообще **переживали** передеплой — стоит проговорить
отдельно, потому что тут легко ошибиться.

**В Docker/`docker-compose`**: файл базы должен физически лежать **внутри примонтированного
volume**, а не просто "рядом с кодом" внутри контейнера. В `docker-compose.yml` каждый из
трёх сервисов (`bot`/`api`/`checkbot`) явно переопределяет
`DATABASE_URL=sqlite+aiosqlite:////app/data/smikhub.db` — путь внутрь `smikhub-data:/app/data`.
**Не убирайте этот `environment:` override и не меняйте путь**, не поправив совпадающий
volume — если `DATABASE_URL` укажет мимо примонтированной директории (например, обратно на
относительный `./smikhub.db`), файл будет создаваться заново в файловом слое контейнера при
каждом `docker compose up --build`/пересоздании контейнера, и вся БД (боты, заказы, баланс)
обнулится, хотя сам volume останется на месте и будет выглядеть подключённым.

**Без Docker** (прямой запуск `python -m smikhub.bot.main` на VPS): относительный путь из
`.env.example` безопасен, пока рабочая директория процесса не меняется между деплоями. Если
деплой-скрипт делает `git clone`/распаковку в новую директорию или чистит папку перед
копированием нового кода — файл `smikhub.db`, лежащий рядом с кодом, будет потерян тем же
способом. В этом случае держите `DATABASE_URL` указывающим на путь **вне** директории с
кодом (например, на отдельную персистентную директорию на диске VPS), либо используйте
внешнюю БД (Postgres и т.п. — код на SQLAlchemy, замена URL не требует правок кода).

**Как проверить, что база реально персистентна**: остановите и заново поднимите
бота/контейнер, не трогая том/директорию с БД, и убедитесь, что ранее подключённые боты
никуда не делись. Если делись — проблема в пути, а не в самой платформе.

## 1. Send Crypto Pay (пополнение и вывод баланса)

Даёт «Кабинету» реальные деньги: `createInvoice` — создание счёта на пополнение,
вебхук — подтверждение оплаты, `transfer` — выплата при одобренном выводе.

### 1.1. Получить токен приложения

1. Откройте `@CryptoBot` (или соответствующего бота Send — сервис-провайдера, на который
   ссылается документация `help.send.tg/en/articles/10279948-crypto-pay-api`).
2. Команда **Crypto Pay → Create App**, привяжите к своему боту.
3. Скопируйте **API Token** приложения — это и есть `SEND_API_TOKEN`.

### 1.2. Заполнить `.env`

```bash
SEND_API_TOKEN=<токен из шага 1.1>
SEND_API_BASE_URL=https://pay.send.tg/api
```

**Важно:** `SEND_API_BASE_URL` я взял по аналогии с `pay.crypt.bot` (стандарт этого
семейства API) — в доступной мне документации точный адрес не был явно прописан.
**Сверьте его с тем, что показывает панель вашего приложения**, прежде чем полагаться на
реальные платежи; если он другой — просто поменяйте значение в `.env`, в коде он нигде не
захардкожен (`smikhub/services/send_pay.py`).

### 1.3. Включить приём платежей (разрешить transfer)

В настройках приложения (там же, где токен) включите **Transfers** — без этого `transfer`
(выплаты при одобрении вывода) будет отклоняться API, даже если токен верный.

### 1.4. Настроить вебхук

В настройках приложения укажите URL вебхука:

```
https://<ваш-домен>/webhooks/send-pay
```

Это должен быть **публично доступный HTTPS**-адрес, на котором крутится
`smikhub.api.main:app` (см. `## Запуск` в README — `uvicorn smikhub.api.main:app`).
Для локальной разработки нужен туннель (ngrok, Cloudflare Tunnel и т.п.) — сервис Send не
достучится до `localhost`.

Каждый вебхук подписывается заголовком `crypto-pay-api-signature` —
`HMAC-SHA256(sha256(SEND_API_TOKEN), тело запроса)`. Проверка — в
`smikhub/services/send_pay.py::verify_signature`, вызывается из
`smikhub/api/routers/webhooks.py`. Если подпись не совпадёт (например, из-за неверного
токена в `.env`), вебхук отклоняется с 401 — деньги не зачислятся молча неправильно, а
запрос просто отвалится, что будет видно в логах API.

### 1.5. Что если не настраивать

Без `SEND_API_TOKEN` «Кабинет» показывает баланс, но при попытке пополнить/вывести бот
отвечает понятным сообщением («сервис оплаты не настроен») вместо ошибки — см.
`smikhub/bot/handlers/cabinet.py`.

### 1.6. Что я не смог проверить сам

У меня нет реального токена и публичного HTTPS для вебхука — живой платёж, реальный
вебхук и реальную выплату через `transfer` я не тестировал. Код написан строго по
документации и покрыт юнит-тестами на детерминированную часть (подпись, идемпотентность
обработки вебхука, резерв/возврат баланса при выводе — `tests/test_send_pay.py`,
`tests/test_webhook.py`, `tests/test_platform_repo.py`), но финальную сквозную проверку с
реальными деньгами нужно сделать самим.

## 2. Check-бот (проверка вступлений в «Купить ОП»)

Отдельный Telegram-бот, которого рекламодатель добавляет админом в свой канал/чат — только
через него платформа видит реальные вступления/отписки и может честно списывать баланс за
подтверждённый трафик.

### 2.1. Создать бота

1. `@BotFather` → `/newbot` → получите токен **второго**, отдельного от основного бота.
2. Это `CHECK_BOT_TOKEN` — не путайте с `BOT_TOKEN` основного бота SmikHub.

### 2.2. Заполнить `.env`

```bash
CHECK_BOT_TOKEN=<токен check-бота>
```

### 2.3. Запустить как отдельный процесс

```bash
python -m smikhub.checkbot.main
```

Это отдельный polling-цикл, независимый от основного бота и API (см. `docker-compose.yml`
— там уже есть сервис `checkbot`, поднимается вместе с остальными через
`docker compose up --build`).

### 2.4. Как это выглядит для рекламодателя

При создании заказа с назначением «Канал/чат» бот сам покажет кнопки для добавления
check-бота в администраторы (`order_admin_kb` в `smikhub/bot/keyboards.py`) — вручную
никому ничего объяснять не нужно, кроме самого факта «нужно выдать боту права админа»,
который стандартен для Telegram.

### 2.5. Ограничение, о котором стоит знать

Поддерживаются только **публичные** ссылки на канал/чат (`t.me/username`). Причина не в
лени, а в самом Bot API: узнать `chat_id` по приватной инвайт-ссылке нельзя, пока бот уже
не состоит в чате — а значит нет безопасного способа привязать такую ссылку именно к
нужному заказу, не рискуя перепутать чужие приватные чаты. Подробнее — в README, раздел
«Проверка вступлений — check-бот».

## 3. Доступ к админ-панели

Без интеграции, но тоже нужно один раз настроить:

```bash
ADMIN_USER_IDS=123456789,987654321
```

Свой Telegram ID можно узнать, например, у `@userinfobot`. Список проверяется на уровне
роутера (`smikhub/bot/admin_guard.py`) — действует и на команду `/admin`, и на все колбэки
внутри панели, не только на первый вход.

## 4. Flyer / Tgrass / PiarFlow (реальная выдача спонсоров) и Subgram

В отличие от Send Pay и check-бота, эти сети подключаются **не через `.env` платформы**, а
самим владельцем бота из раздела «🤖 Продать ОП → статус бота» — каждый владелец вводит свой
ключ API. Настраивать это на уровне сервера не нужно. Но, в отличие от прошлой версии этого
документа, ключ теперь не просто хранится — им реально пользуется backend, чтобы получать
живые спонсорские задачи и сверять их выполнение.

### 4.1. Откуда взять ключ каждой сети

- **Flyer** (`api.flyerhubs.com`) — ключ, который вы получаете при регистрации бота в
  Flyer (кнопка «✅ Flyer» в панели бота даёт ссылку и инструкцию).
- **Tgrass** (`tgrass.space`) — зарегистрируйте бота в `@tgrassbot`, получите ключ
  авторизации (заголовок `Auth`).
- **PiarFlow** (`piarflow.com`) — **можно в одно касание**: на экране подключения PiarFlow
  есть кнопка «🔗 Подключить автоматически» — backend сам вызывает `POST /traffic_bot/add`
  с токеном бота и Telegram ID владельца и получает ключ, вставлять его руками не нужно.
  Ручной ввод ключа (`Authorization: Bearer`) остаётся рабочим запасным вариантом, если
  авто-подключение не сработает.
- **Subgram** — токен по-прежнему только сохраняется (кнопка «✅ Subgram» в панели бота
  работает как раньше), реальных вызовов к его API нет: пользователь не присылал
  документацию по Subgram, а угадывать формат чужого API я не стал.

### 4.2. Как это работает технически

Ключ каждой сети шифруется и хранится в `SponsorIntegration`
(`smikhub/db/models.py`), привязан к конкретному боту и сети. Клиенты сетей —
`smikhub/services/sponsor_providers/{flyer,tgrass,piarflow}.py`, тонкие обёртки на
`aiohttp`, без побочных эффектов, написаны строго по документации, которую прислал
пользователь (`tgrass.space/integration`, `piarflow.com/api-docs`,
`api.flyerhubs.com/openapi.json`).

**Бот владельца** (не SmikHub, а его собственный код) дёргает наш backend API двумя
эндпоинтами, используя «🔑 Токен интеграции» из панели бота (заголовок `Auth`, как и у
`/config`):

- `GET /api/v1/bot/sponsors?user_id=&chat_id=&is_premium=&lang=` — отдаёт до
  `bot.max_sponsors` задач из подключённых сетей, в порядке приоритета площадок
  (`🔀 Приоритет` в панели бота), отфильтрованных по `bot.min_price`.
- `POST /api/v1/bot/sponsors/check` — тело `{"user_id": …, "tasks": [{"provider","task_id"}]}`
  — проверяет, выполнил ли пользователь конкретные задачи, группируя запрос по сетям.

Логика — `smikhub/api/routers/sponsors.py`.

### 4.3. Реальный пол/возраст/страна из Tgrass

У Tgrass есть `GET /subscriber/{id}` — профиль пользователя, если он уже известен их сети
(пол, возраст, страна, premium). Если у бота подключён Tgrass, backend перед выдачей один
раз запрашивает профиль пользователя и, если Tgrass его знает, реально применяет фильтры
`gender`/`age_group`/`excluded_countries` заказов «botohub» — раньше это честно не
работало из-за отсутствия источника данных, теперь работает, но только для пользователей,
уже встречавшихся Tgrass. Сбой запроса к Tgrass не ломает `/sponsors` — фильтры просто не
применяются, как и раньше.

### 4.4. Реальная статистика в панели бота

«📈 Статистика» больше не заглушка — для каждой подключённой сети запрашиваются реальные
данные за сегодня:
- **Tgrass**: `GET /balance` + `GET /statistics?date=` (баланс, подписки/отписки, доход).
- **PiarFlow**: `GET /traffic_bot` + `GET /traffic_bot/stats?date=`.
- **Flyer**: только статус ключа (`GET /get_me` → `bot_id`/`webhook`/`status`) — по
  доступной документации у Flyer нет отдельного эндпоинта агрегированной статистики
  дохода, поэтому цифр дохода для него не показываю.
- **Subgram**: как и с выдачей спонсоров — без документации API отображается как «нет
  данных», а не выдуманные цифры.

Если сеть не ответила — её блок показывает «данные временно недоступны», остальные блоки
всё равно отрисовываются (`asyncio.gather(..., return_exceptions=True)` в
`smikhub/bot/handlers/stats.py`).

### 4.5. Ограничения, о которых стоит знать заранее

- **Тематики бота не фильтруют спонсоров вообще нигде** — ни у внешних сетей, ни у своего
  инвентаря `botohub`. Ни один из трёх API (по документации, которая была доступна) не
  возвращает категорию/тематику оффера, а у нашей собственной модели данных нет единого
  поля "тематика" ни у бота, ни у заказа — сопоставлять нечего. «🚫 Отключенные тематики»
  сейчас ни на что не влияет.
- **У Tgrass нет цены оффера в `/offers`** — его задачи проходят фильтр «Мин. цена»
  безусловно, им нельзя назначить порог.
- **Собственный инвентарь платформы (`botohub`, из «Купить ОП») уже участвует в выдаче** —
  `/sponsors` смешивает реальные заказы «Купить ОП» (только с назначением «Канал/чат» и
  подтверждённым check-ботом) с внешними сетями по приоритету бота, с реальным учётом
  `is_premium`/языка/пола/возраста/страны (последние три — только если подключён Tgrass и
  знает пользователя). Подробности — в `docs/api-integration.md`.
- **`/traffic_bot/add` у PiarFlow я не проверял вживую** — доке не было явного указания,
  требует ли этот эндпоинт какой-то предварительной авторизации помимо самого запроса.
  Поэтому ручной ввод ключа остаётся полноценным запасным вариантом на экране подключения,
  а не убран в пользу авто-режима.

### 4.6. Что я не смог проверить сам

У меня нет боевых ключей ни для одной из трёх сетей — живой вызов `/api/v1/bot/sponsors`
с реальными данными я не делал. Нормализация ответов каждой сети (маппинг полей, обработка
статусов) покрыта юнит-тестами на задокументированных форматах
(`tests/test_sponsor_providers.py`), агрегация/приоритет/фильтры — тестами на уровне
эндпоинта (`tests/test_sponsors_api.py`). Финальную проверку с реальными ключами и
реальными пользователями нужно сделать самим — если формат ответа какой-то сети на практике
отличается от документации, поправить нужно только соответствующий файл в
`smikhub/services/sponsor_providers/`, остальной код их не касается.
